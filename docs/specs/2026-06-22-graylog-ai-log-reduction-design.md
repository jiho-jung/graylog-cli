# Graylog 대량 로그 AI 분석용 축약 설계

## Summary

Graylog API에서 장애 시간대 로그를 직접 가져오되, AI에 원본 로그 전체를 넣지 않고
먼저 결정론적 축약을 수행한다. 목표는 대량 로그 기준 원본의 1-3% 크기 Markdown
사건 브리프로 줄이면서, 장애 원인 추적과 이상 징후 탐지에 필요한 시간 순서, 희귀 패턴,
급증 패턴, 가명화된 대표 로그를 보존하는 것이다. 작은 샘플이나 장애 신호가 밀집된
구간에서는 축약률보다 신호 보존을 우선한다.

이 문서는 운영 절차와 분석 파이프라인의 상위 설계를 다룬다. 구체적인 CLI 명령,
패키지 구조, 함수 시그니처, 테스트 구현 단위는 별도 implementation plan에서 다룬다.

## Goals

- 장애 시간대 대량 로그를 AI가 처리 가능한 크기의 사건 브리프로 축약한다.
- 원본 민감값을 AI 입력에 넣지 않고, 같은 원문 값은 문서 전체에서 같은 별칭으로 유지한다.
- 반복 정상 로그는 카운트 중심으로 줄이고, 장애 원인 후보가 될 신호는 누락하지 않는다.
- 사람이 Graylog에서 원본을 재조회할 수 있는 단서와 상대 시간 정보를 남긴다.
- AI가 분석하기 쉬운 구조와 운영자가 바로 읽을 수 있는 재조회 단서를 함께 제공한다.

## Data Collection

- Graylog API 조회는 시간창을 나눠 수행한다.
  - 기본 개념: 장애 추정 시각 전후의 분석 창
  - 절대 from/to와 최근 1h/8h 같은 상대 범위도 운영 입력으로 허용
  - 로그가 너무 많으면 1-5분 단위로 분할 조회
  - 우선 필드:
    timestamp, level, application, hostname, spc_service, spc_tier, part, pid,
    message, source, Graylog message id
- 조회 조건은 운영자가 지정한 query, from/to, streams 또는 filters, limit/page,
  fields allowlist를 따른다.
- 구체적인 실행 옵션 이름과 기본값은 구현 계획에서 정한다.

## Preprocessing

- AI 입력 전처리 단계는 원본 로그를 바로 요약하지 않고, 먼저 보안 처리와 패턴화를 수행한다.
- IP, UUID, VPC/ENI/ARN/account-like 값은 기본 민감값 목록으로 보고 일관 가명화한다.
  - 예: 같은 실제 IP는 문서 전체에서 `IP_001`로 유지
  - 원문 값은 AI 입력에 넣지 않음
- 조직별 식별자, tenant id, customer id 같은 도메인 특화 민감값은 정책으로 추가할 수 있다.
- 숫자, 포트, sequence, elapsed time, ID류 동적 값은 패턴 군집용으로 정규화한다.
- 기본 그룹핑 기준은 정규화된 message이며, 같은 정규화 메시지는 하나의 패턴으로 묶는다.
- 필요하면 host, application, service 같은 메타 필드를 그룹핑 기준에 포함할 수 있다.
- 가명화와 정규화의 필드별 적용 범위는 운영자가 실행 정책으로 조정할 수 있다.
  - 기본 정책은 민감값 노출을 줄이는 보안 기본값을 제공한다.
  - Graylog 재조회에 필요한 message id와 상대 시간은 보존한다.

## Pattern Reduction

각 패턴은 다음 정보만 보존한다.

- 총 건수, 최초/최후 시각, 레벨 분포
- application/hostname/part 상위 분포
- 가명화된 대표 로그 1-3개
- 장애 시각 근처 샘플 1개
- 최초 발생 샘플 1개

반복적인 정상 info/debug 로그는 카운트와 분포 중심으로 줄인다. 기준선 확인이 필요할 때만
최소 대표 샘플을 남긴다. 반대로 error, warn, fatal, panic은 우선 보존하며, 장애 원인
후보가 될 수 있는 신호로 별도 표시한다.

## Anomaly Signals

다음 패턴은 최종 브리프에서 별도 섹션이나 표시로 보존한다.

- error, warn, fatal, panic 등 높은 우선순위 레벨
- 장애 시간대에 새로 등장한 패턴
- 짧은 시간에 급증한 패턴
- 특정 host, application, service, part에 치우친 패턴
- 전체 건수는 적지만 장애 시각 근처에 등장한 희귀 패턴

여러 이상 신호가 동시에 많을 때는 원인 후보 가능성이 높은 신호를 먼저 보여준다. 기본
우선순위는 높은 우선순위 레벨, 신규 패턴, 급증 패턴, 편중 패턴, 희귀 패턴 순이다.
시간순 흐름은 별도 타임라인에서 보존한다.

## Output

최종 출력은 사람이 AI에 붙여넣고 운영자가 함께 읽는 Markdown 사건 브리프다. 브리프는
원본 로그 덤프가 아니라 가명화된 사건 요약 문서이며, 다음 섹션을 포함한다.

- 요약
- 타임라인
- 상위 오류/경고 패턴
- 희귀/신규 패턴
- 호스트/서비스 편중
- 대표 로그
- AI에게 물어볼 분석 질문
- 필요 시 Graylog 재조회 키워드

재조회 단서는 message id, 상대 또는 절대 시간, 패턴 키워드 조합으로 남긴다. 원문
민감값을 직접 노출하지 않는 범위에서 Graylog 원본으로 돌아갈 수 있게 한다.

## Operational Interface

입력은 Graylog API 검색 조건과 분석 정책이다.

- query
- 장애 추정 시각 기반 시간창, 절대 from/to, 상대 시간 범위
- streams 또는 filters
- limit/page 또는 chunk 단위 조회 정책
- fields allowlist
- redaction policy
- normalization policy
- partial result and quality warning policy

출력은 Markdown 사건 브리프다. 기본 보안 정책은 일관 가명화이며, 원문 민감값을 AI 입력에
넣지 않는다. 재조회가 필요한 경우 message id, 상대 시간, 패턴 키워드처럼 원본으로
돌아갈 수 있는 단서를 남긴다.

일부 조회, 파싱, 축약 단계가 실패해도 가능한 로그로 부분 결과를 만들 수 있다. 이 경우
누락된 chunk, 파싱 실패 수, 처리 상한 도달 여부 같은 품질 정보를 경고로 표시한다.

## Test Plan

- 작은 샘플 로그로 같은 에러가 하나의 정규화 패턴으로 묶이는지 확인한다.
- 작은 샘플 로그로 같은 IP/ENI/VPC/UUID/ARN이 항상 같은 별칭으로 치환되는지 확인한다.
- 작은 샘플 로그로 반복 정상 로그가 카운트 중심으로 줄고 대표 로그가 과도하게 늘지 않는지
  확인한다.
- 장애 시각 직전 최초 error/warn 패턴이 누락되지 않는지 확인한다.
- 특정 host/application/service에 몰린 오류가 별도 섹션에 드러나는지 확인한다.
- 부분 조회 실패나 파싱 실패가 있을 때 브리프에 품질 경고가 포함되는지 확인한다.
- 대량 샘플에서 최종 Markdown 크기가 원본 대비 1-3% 목표 범위에 들어오는지 측정한다.
- 장애 신호가 밀집된 샘플에서는 축약률보다 error/warn, 신규, 급증, 편중 신호가 보존되는지
  확인한다.

## Assumptions

- 이번 범위는 저장소 코드 수정 세부가 아니라 운영 절차와 분석 파이프라인의 상위 설계다.
- 구체적인 CLI, 패키지 구조, 함수 시그니처, 테스트 작업은 별도 implementation plan에서 다룬다.
- Graylog 로그는 API로 조회한다.
- 최종 산출물은 Markdown 사건 브리프다.
- 목표 축약률은 대량 로그 기준 원본의 1-3%다.
- 주요 목적은 장애 원인 추적과 이상 징후 탐지를 함께 지원하는 것이다.
